# ADR-0020: The migration seeds the question bank, and guards the one local administrator

**Status:** Accepted
**Date:** 2026-08-22

## Context

Two different things have to be in a database before anybody can use it:

1. **The question set.** The form is rows, not columns (ADR-0016), so a database
   with no `questions` rows is a form that asks nothing. A clean install has to
   ask exactly the Typeform question set in `docs/form-spec.md`, or a report
   filed on day one is not comparable with the archive it joins.
2. **Somebody who can sign in.** The admin UI is gated by an allowlist in
   `admin_users`. An empty allowlist locks everyone out, including the developer
   who created the database thirty seconds ago.

Those two look alike and are not. The question set is the same everywhere,
including production. An administrator is a real person, and the list of them is
not something to invent in source control.

## Decision

### The question bank is seeded by the migration, written as SQL, not `HasData`

`QuestionBankSeed` transcribes `docs/form-spec.md` into data;
`QuestionBankSeedWriter` writes it through `MigrationBuilder.InsertData`;
`InitialSchema` calls it after creating the tables.

**Not `HasData`.** `HasData` makes seed rows part of the model snapshot, and the
whole point of ADR-0016 is that an administrator rewords, reorders, retypes, and
deletes these rows after deployment. Every one of those edits would then show up
as a model difference that the next scaffolded migration tries to undo. Seed data
that the application is expected to edit does not belong in the model.

Identifiers are derived from the question key with SHA-256 (`SeedIds`) rather
than drawn at random, so the migration produces identical rows on every database
and in a generated SQL script.

`QuestionBankSeedTests` reads `docs/form-spec.md` at test time and fails if the
seed and the spec drift apart — label, section, type, choices, and help text.
The spec is generated by `tools/extract-typeform.py` and is never hand-edited,
so the test compares against the source of truth rather than a second copy of it.

### Exactly one obviously-fake local administrator, guarded in SQL

`admin@localhost`, role `administrator`. Nothing can be delivered to that
address, nobody can receive at it, and it is recognisable as a development
artefact at a glance.

**The guard is a PostgreSQL setting read at apply time**, not a C# condition:

```sql
INSERT INTO admin_users (...)
SELECT ...
WHERE current_setting('hpac.seed_development_admin', true) = 'true'
  AND NOT EXISTS (SELECT 1 FROM admin_users WHERE member_identifier = 'admin@localhost');
```

A development connection string opts in with
`Options=-c hpac.seed_development_admin=true`. Unset — which every database is
until somebody says otherwise — means no.

A C# guard on `ASPNETCORE_ENVIRONMENT` would be evaluated on whichever machine
ran `dotnet ef migrations script`, so a script generated on a laptop would carry
the insert into production with the guard already resolved to "yes". Reading a
setting at apply time puts the decision on the database being changed, which is
the only machine that knows whether it is production.

### The real allowlist is not here

The safety-officer allowlist is a list of real people. It is a later issue, and
it belongs in an operational process — with a record of who added whom — rather
than in a migration in a public repository. No migration in this repository will
ever contain a real name or a real address.

### The French wording is seeded machine-translated, and says so

`docs/form-spec.md` is English, because Typeform held one language. A clean
database has to ask the form in **both**, so every seeded question carries a
French counterpart with `is_source = false` and `is_machine_translated = true` —
the state ADR-0016 already defines as "renders, reviewed by nobody".

`is_source` records which language the wording was authored in, not which one
matters. The French rows are not a lesser copy of the English ones; they are the
French half of a bilingual question set that happens to have been written down
in English first.

The flag is a mapped column, not a comment, so the admin UI in #49 can list
every piece of unreviewed wording and a safety officer can work through it.
`ReviseByHand` clears it, which is how reviewed French becomes reviewed French.
`SeededQuestionBankTests` asserts both halves of that: the French rows are
marked machine-translated, and they are findable by that mark alone.

The risk this accepts is a **quality** one — wording that reads as translated
until somebody improves it. It is not a privacy one: no reporter's data passes
through it, and nothing here reaches a published summary.

## Consequences

- A clean `dotnet ef database update` produces a database that asks the real
  form, in both languages, immediately.
- Drift between `docs/form-spec.md` and the seed fails a test rather than
  shipping a form that quietly stopped matching.
- The seeded rows are ordinary rows. An administrator edits them like any other,
  and nothing tries to put them back.
- Re-seeding an existing database is not a thing this migration does. Changing
  the question set after deployment is an administrator's job through the admin
  UI, not a new migration — which is the outcome ADR-0016 wanted.
- A developer who forgets the `Options=` fragment gets an empty allowlist and no
  way in. That is the failure this trades for, deliberately: locked out is
  recoverable, a stray administrator in production is not.
- The French wording will read as machine-translated until somebody reviews it.

## Alternatives rejected

**`HasData`.** Idiomatic EF, and the model snapshot then knows the rows. Rejected
for exactly that reason — see above.

**Seeding at application start-up instead of in a migration.** Tempting, because
start-up code can read configuration. Rejected: it makes "what is in this
database" depend on which application booted against it and when, and it races
between instances. A schema change and the data that has to accompany it belong
in the same versioned step.

**Guarding the administrator seed on `ASPNETCORE_ENVIRONMENT` in C#.** Rejected:
it is resolved at script-generation time. See above.

**Seeding no administrator at all, and documenting a manual `INSERT`.** Safest
of all, and it makes a clean checkout a worse experience for no security gain
over a guard that already fails closed.

**Seeding the real safety officers.** Rejected outright. Real names and
addresses do not go into a public repository, and an allowlist that changes
needs a process rather than a migration.

**Leaving the French wording out and seeding the questions inactive until a
francophone has reviewed it.** The most honest-looking option: nothing claims to
be French that nobody has read.

Rejected, and worth saying why at length, because it is the option that sounds
most careful:

- A question cannot be activated with a missing counterpart (ADR-0016), so this
  produces a clean database whose form asks **nothing at all** — in either
  language. "Careful about French" would have cost the English form too.
- It would block the end-to-end journey in #27, which runs submit → summarize →
  review → approve in both locales. A suite that cannot run in French is a suite
  that stops noticing French regressions.
- It treats French as the optional half. This application has no optional half —
  see `AGENTS.md`, "Both languages are first-class".
- The domain already models exactly this situation. `is_machine_translated` says
  "renders, reviewed by nobody", and hiding the wording instead of marking it
  discards information a reviewer needs.
