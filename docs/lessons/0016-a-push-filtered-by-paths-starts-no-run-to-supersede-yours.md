# Lesson 0016 — A push filtered by paths starts no run to supersede yours

## Symptom

On PR #392, push 60e0f25 started both `traceability.yml` and
`i18n-translate.yml`. The translation bot pushed b863066 first. The
traceability bot's push was rejected (`! [rejected] … (fetch first)`), and
the required `docs` check stayed red until the matrix was regenerated by hand.

## Root cause

A rejected push was read as "somebody pushed, and their push starts its own
run" ([ADR-0106](../decisions/ADR-0106-every-line-of-the-matrix-derives-from-one-source-item.md)
point 4). GitHub evaluates `pull_request_target` `paths` against each push,
and b863066 changed only `locales/fr-CA*.json`. It started CI, and no run of
either bot. The rule was written for an author racing a bot, and nobody asked
what happens when two bots race each other. Under ADR-0106's handler, the
same race would have ended green with `docs` still red.

## Spec delta

[ADR-0113](../decisions/ADR-0113-a-bot-pushing-onto-a-pull-request-replays-past-another-bot.md):
both bots push through `tools/push-to-pr-branch.mjs`. A newer push that
changed one of the workflow's trigger paths supersedes the run. A newer push
that changed none gets the commit replayed on top of it.

## Scenario

No scenario. This is a property of the delivery tooling, not of the system
`features/` describes. `tests/js/push-to-pr-branch.test.mjs` proves it
against real repositories, and fails when a workflow's `--paths` drifts from
its trigger paths.

## Skill

[`deliver-hpac-change`](../../skills/deliver-hpac-change/SKILL.md) now says
that a workflow committing onto a pull request's branch pushes through
`tools/push-to-pr-branch.mjs`, never a bare `git push`. "Someone else's run
will redo it" holds only when that push matches your workflow's `paths`.

Since #492 the general rule lives in the generic
[`deliver-change`](../../skills/deliver-change/SKILL.md) skill; the project skill named above
keeps this repository's commands, paths, and references.
